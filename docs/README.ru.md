# Отчёт о GitHub-профиле

Инструмент собирает публичные данные GitHub и показывает, что видно в профиле
разработчика: собственные проекты, форки, PR, issues и состояние репозиториев.

**Он не вычисляет Legion Score и не обещает рост скора или аллокацию.**

Если GitHub явно сообщает, что репозиторий пуст, отчёт показывает ноль коммитов
и отсутствие файлов. Общая ошибка `409` или недоступное дерево остаются неизвестными
данными: один HTTP-статус не доказывает отсутствие кода.

Повторяющиеся репозитории и SHA коммитов учитываются один раз. При повторах
список помечается неполным: изменение порядка страниц может также скрыть записи.

Сообщение GitHub о вторичном лимите останавливает дальнейшие запросы, даже если
заголовок `Retry-After` отсутствует и основная квота ещё доступна. Обычная ошибка
прав доступа не блокирует остальные проверки.

## Запуск

Нужен Node.js 22 или новее. Устанавливать зависимости не требуется.

```sh
git clone https://github.com/Crypto-Kucherov/crypto-dapp.git
cd crypto-dapp
node src/index.js Crypto-Kucherov
```

Отчёт в Markdown:

```sh
node src/index.js Crypto-Kucherov --out reports/profile.md
```

Отчёт в JSON:

```sh
node src/index.js Crypto-Kucherov --format json --out reports/profile.json
```

По умолчанию анализируется активность за 90 дней. Начальную дату и число
подробно проверяемых репозиториев можно изменить:

```sh
node src/index.js Crypto-Kucherov --since 2026-01-01 --max-repos 5
```

Конечный день периода задаётся через `--until`, например:

```sh
node src/index.js Crypto-Kucherov --since 2026-08-01 --until 2026-08-31
```

Прошедший день включается целиком по UTC; сегодняшний — только до начала запуска.
Будущая дата или начало позже конца отклоняются до запросов к GitHub.
Без `--since` берутся 90 дней до выбранного конца. Дата генерации остаётся реальной:
исторический период ограничивает активность, но файлы и релизы проверяются в текущем
состоянии. В режимах `--from` и `--compare` параметр `--until` недоступен.

Каждому снимку давайте новое имя: существующие файлы не перезаписываются.
Отчёты в папке `reports/` исключены из Git.

## Отчёт для браузера

```sh
node src/index.js Crypto-Kucherov --format html --out reports/profile.html
```

Откройте полученный файл в браузере. Он показывает показатели профиля,
состояние репозиториев, даты и ограничения данных. Отчёт можно отправить
одним файлом или распечатать из браузера; оформление адаптируется к телефону.

Сбор свежих данных требует доступа к GitHub. Уже сохранённый HTML работает
без сети: в нём нет скриптов, внешних шрифтов, картинок и других загружаемых
ресурсов. Ссылки на GitHub открываются только при переходе по ним.
Содержимое GitHub экранируется, а политика безопасности блокирует скрипты
и внешние ресурсы. Данные в открытом файле автоматически не обновляются.

Для последующих сравнений сохраняйте JSON: HTML не подходит как входной снимок.
Можно скачать и открыть [пример профиля](../examples/profile.html) или
[пример сравнения](../examples/comparison.html). Оба используют сохранённые
публичные данные от 27 сентября 2026 года.

## Преобразование сохранённого профиля

Для преобразования одного сохранённого JSON-профиля используйте `--from`:

```sh
node src/index.js --from reports/profile.json --format html --out reports/profile.html
node src/index.js --from reports/profile.json --out reports/profile.md
```

GitHub не вызывается, токен не нужен. Даты, счётчики, рекомендации и предупреждения
остаются исходными; `apiRequests` относится к первоначальному сбору данных.
Поддерживаются профильные JSON-экспорты схемы 1, включая v0.1 и отчёты с явно
неполными данными. JSON-сравнения не подходят. Некорректная структура и
противоречивые счётчики покрытия отклоняются. Существующие файлы защищены от перезаписи.
В этом режиме доступны `--format`, `--out` и `--fail-on-incomplete`.

## Сравнение двух отчётов

Новые снимки сохраняют ID репозиториев GitHub. Совпадающий ID позволяет сопоставить
репозиторий после переименования. Если имя прежнее, а ID изменился, показатели
двух разных репозиториев не сравниваются. Старые снимки без ID поддерживаются
через сопоставление имён, но не позволяют выявить пересоздание под прежним именем.

Сравнение работает без сети и токена. Сначала укажите старый JSON-отчёт,
затем новый:

```sh
node src/index.js --compare reports/before.json reports/after.json
node src/index.js --compare reports/before.json reports/after.json --format json --out reports/changes.json
node src/index.js --compare reports/before.json reports/after.json --format html --out reports/changes.html
```

Готовый пример можно запустить сразу после скачивания проекта:

```sh
node src/index.js --compare examples/crypto-kucherov.json examples/crypto-kucherov-after.json
```

[Пример сравнения](../examples/comparison.md) показывает состояние публичного
профиля до и после первого релиза 27 сентября 2026 года. Это сохранённые данные,
а не текущая статистика.

Инструмент сравнит счётчики PR, issues и коммитов, видимость репозиториев,
наличие тестов, CI, README, лицензии, исходников и релизов.

Для сравнения активности сохраняйте отчёты с одинаковой начальной датой
`--since`, например `--since 2026-01-01`. Если изменился период анализа,
не хватает данных или сменилась основная ветка, соответствующий прирост
будет помечен как `Not comparable`, а не вычислен из несопоставимых чисел.

`Unknown` остаётся неизвестным значением. Репозиторий, который не попал
в ограниченную выборку, не считается удалённым. Разница счётчиков при
расширении периода — чистое изменение: на него влияют также индексация,
перезапись истории и видимость, поэтому это не доказательство нового вклада.

Отчёты должны принадлежать одному аккаунту и идти от старого к новому.
Поддерживаются JSON-отчёты версии схемы 1, в том числе из v0.1.
Параметры `--since` и `--max-repos` в режиме сравнения не применяются:
они задаются при первоначальном сборе каждого отчёта.

## Что означают результаты

- Собственные проекты, форки и архивные репозитории показаны отдельно.
- Коммиты считаются только для выбранного автора в основной ветке проверяемых
  репозиториев. Это не календарь contributions в профиле GitHub.
- PR и issues считаются по дате создания, внешние принятые PR — по дате слияния.
  «Внешний» означает репозиторий, владельцем которого является другой аккаунт.
- README, лицензия, тесты и GitHub Actions определяются по именам файлов.
  README ищется в корне, `.github/` и `docs/`: эти расположения поддерживает GitHub.
  README внутри вложенного пакета или руководства не заменяет README репозитория.
  Наличие теста не означает, что он проходит; наличие workflow не означает успешный CI.
- `Unknown` означает, что проверку не удалось завершить. Это не ноль и не отсутствие файла.
- `incomplete` означает неполные данные; ограничения перечислены в отчёте.
- Форки и архивные репозитории перечисляются без подробной проверки.

Папка `tests/` только с README или JSON-данными больше не считается наличием
тестового кода. Для такого признака нужен файл с распознаваемым расширением
исходников. Поддерживаются, например, `Vault.t.sol`, `UserTest.java`,
`CalculatorTests.cs`, `UserTest.php`, `parser_spec.rb` и `parser_test.exs`,
а также ранее поддерживаемые имена JavaScript, TypeScript, Python и Go.
Это проверка имён, а не содержимого или результатов запуска: вспомогательный
код тоже может совпасть с шаблоном, а встроенные в обычный файл тесты — остаться
незамеченными. Полные шаблоны перечислены в [README](../README.md#recognized-test-paths).
При неполном дереве отсутствие совпадения остаётся `Unknown`.
При `--from` старые проверки сохраняются; новые правила применяются при свежем сборе.

Полные ограничения, структура отчёта и источники описаны в [README](../README.md).
[Пример отчёта](../examples/crypto-kucherov.md) — снимок публичных данных с указанной датой,
а не текущая статистика и не оценка качества разработчика.

## Лимиты и ошибки

Для небольшого профиля токен обычно не нужен. При превышении лимитов GitHub
повторите запуск позже или используйте переменную окружения `GITHUB_TOKEN`,
настроенную через ваш обычный способ хранения секретов. Права на запись не нужны.
Не присылайте токены в issues и не добавляйте их в репозиторий.

Инструмент делает только запросы на чтение публичных данных. Он ничего не
публикует, не создаёт коммиты и не подключается к кошельку. Приватные репозитории
не включаются в отчёт даже при наличии токена.

## Проверка кода

Для автоматической проверки полноты отчёта добавьте `--fail-on-incomplete`:

```sh
node src/index.js Crypto-Kucherov --fail-on-incomplete --format json --out reports/check.json
node src/index.js --from reports/check.json --fail-on-incomplete
```

При неполных или неизвестных данных отчёт всё равно сохраняется, но программа
завершается с кодом `2`. Код `0` означает успешное завершение, `1` — ошибку,
которая не позволила сформировать отчёт. Без флага неполный отчёт по-прежнему
возвращает `0` с предупреждениями. Отсутствие тестов или релиза само по себе
не считается неполнотой данных. Намеренно пропущенные форки, архивы и проекты
за пределами `--max-repos` тоже не вызывают код `2`. Флаг неприменим к `--compare`.

### Тесты проекта

```sh
node --test
```

Тесты работают без сети и токенов. Полезные изменения: исправления ошибок,
проверки важных случаев, улучшение инструкций и примеров.
